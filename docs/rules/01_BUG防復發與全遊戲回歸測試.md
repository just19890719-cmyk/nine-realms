# 《諸神鐵匠》永久開發規則｜BUG 防復發與全遊戲回歸測試

（Mochi 2026-10-25 15:56 定，原文照錄）

## 一、最高優先原則
從現在開始，每次修改《諸神鐵匠》的任何程式碼，包括 BUG 修復、UI 調整、功能新增、系統重構，都必須執行影響範圍分析與回歸測試。
禁止只修復使用者回報的位置，就直接宣布完成。
使用者只負責遊玩、體驗與提供意見，不應該反覆充當程式測試員。

## 二、每次發現 BUG，必須執行七個步驟
### 1. 追查根本原因
* 先重現 BUG。
* 找出真正的錯誤來源。
* 檢查是否存在重複邏輯、狀態不同步、事件衝突、CSS 覆蓋或資料錯誤。
* 不允許只用額外補丁掩蓋問題。
* 無法重現時，必須說明原因與待確認事項。

### 2. 全專案搜尋同類問題
修復之前，必須搜尋整個程式庫是否存在相同或類似實作。
例如：
* 背包按鈕有問題，檢查其他頁面共用的按鈕。
* 武器強化數值有問題，檢查所有武器品質與強化階級。
* 材料數量有問題，檢查製作、附魔、交易所及存檔。
* 手機排版有問題，檢查所有使用相同元件的頁面。

不能只修改最先發現的那一處。

### 3. 分析連帶影響
每次修改前，必須確認：
* 哪些功能引用了這段程式？
* 哪些頁面共用這個元件？
* 是否影響遊戲資料？
* 是否影響存檔與讀檔？
* 是否影響手機版？
* 是否影響其他系統？

列出受影響的功能與測試範圍。

### 4. 正式修復
* 優先修改問題根源。
* 不重複建立相同功能。
* 不隨意增加 CSS 覆蓋規則。
* 不更改無關的遊戲數值。
* 不破壞既有存檔。
* 修改前保留可回復版本。

### 5. 建立永久回歸測試
每修復一個 BUG，必須新增或更新對應的自動化測試。
例如：
BUG：切換背包分類後，選中的武器資料沒有更新。
除了修復問題，還必須建立測試：
* 切換武器分類
* 切換材料分類
* 重新選取物品
* 展開或收起詳情
* 再次返回原本分類

確保相同錯誤不會在之後的更新再次出現。
修復完成後，測試必須永久保留在專案內。

### 6. 執行全遊戲回歸檢查
每次修改後，依序執行：
* 第一層：BUG 本身的重現測試。
* 第二層：所有受到影響的相關功能測試。
* 第三層：全專案現有自動化測試，包括單元測試、整合測試及可執行的端到端測試。
* 第四層：遊戲核心流程的冒煙測試：鍛造武器 → 強化 → 附魔 → 背包 → 駐守村莊 → 狩獵收益 → 回收材料 → 存檔 → 重新載入。
* 第五層：UI 改動時，額外測試 320px、375px、430px 手機畫面，檢查溢出、遮擋、按鈕及操作功能。

若任何測試失敗，必須修復或明確回報，不得宣稱全部通過。

### 7. 提交測試報告
每次完成修改，必須提供：

BUG 修復報告
* 問題原因：
* 修改檔案：
* 是否搜尋全專案同類問題：
* 發現並修復多少個同類問題：
* 新增哪些永久測試：
* 已執行哪些測試：
* 通過／失敗／未執行結果：
* 是否影響其他功能：
* 是否有尚未排除的風險：

不得在未執行測試時宣稱「已全面測試」。

## 三、建立永久 BUG 紀錄
在專案中建立 BUG_HISTORY.md，記錄：
* BUG 編號
* 發生日期
* 問題描述
* 根本原因
* 修復方式
* 影響系統
* 對應測試
* 是否再次復發

每次出現新問題，先搜尋過去是否曾發生類似錯誤。
若同一 BUG 再次出現，必須優先檢查先前修復是否失效，以及測試為何沒有阻止復發。

## 四、建立自動化測試基礎
請依照現有專案技術架構，建立適用的自動化測試系統。
包含：
* 單元測試
* 系統整合測試
* 核心遊戲流程測試
* 存檔與讀檔測試
* 手機 UI 回歸測試
* 必要的畫面截圖比對

優先重用現有測試工具，不要為了測試引入不必要的複雜架構或付費服務。
所有測試應能透過統一指令執行。

## 五、禁止事項
1. 禁止修完一個 BUG，沒有驗證就宣布完成。
2. 禁止反覆用臨時補丁解決同一個問題。
3. 禁止忽略其他頁面存在的相同程式。
4. 禁止刪除測試來讓結果通過。
5. 禁止擅自修改遊戲平衡、物品資料或存檔格式。
6. 禁止把沒有實際測試過的項目回報為通過。
7. 禁止在未確認安全性的情況下大量重構無關功能。

## 六、工作方式
使用者提出一個 BUG 時，不需要使用者額外要求「順便檢查其他地方」。
你必須自動完成：
根本原因分析 → 全專案搜尋同類問題 → 修復 → 新增永久測試 → 相關功能測試 → 全遊戲回歸檢查 → 提交報告。
這是《諸神鐵匠》的永久開發規則，適用於後續所有程式修改。
如因環境限制無法執行某項測試，必須明確列出未測項目與原因，不能假裝已經完成。
